Row-level security and hardening.
1) Database users: migrator (owns tables, runs prisma migrate deploy) and app_user (NOSUPERUSER, NOBYPASSRLS, select/insert/update/delete only, no DDL). The API connects as app_user.
2) Raw-SQL migration: helper functions app_branch_ids() (reads current_setting('app.branch_ids', true), returns NULL when unset) and app_all_branches() (reads app.all_branches). For clients, leads, appointments, invoices, expenses and attendance_records: ENABLE and FORCE ROW LEVEL SECURITY and a policy branch_isolation with USING and WITH CHECK (app_all_branches() OR branch_id = ANY(app_branch_ids())). The policy must fail closed when the setting is missing. For sensitive child tables without branch_id (assessments, reports, progress_entries, payments, documents) add EXISTS-based policies through their parent. Do not enable RLS on users, roles, role_modules, role_permissions or audit_logs (login needs them before any branch context exists).
3) Extend the Prisma branch extension: run every query inside a transaction that first calls set_config('app.branch_ids', <ids>, true) and set_config('app.all_branches', <true|false>, true) with parameters (never string-built, never session-wide SET). Branch ids come from the user's UserBranch rows loaded by AuthGuard, never from request input. Multi-step writes use one interactive transaction that sets the context at its start.
4) BullMQ workers, seeds and scripts have no user: give them an explicit context (all_branches = true) set in code, or a dedicated documented role, and never use the app_user credentials with BYPASSRLS.
5) Tests run as app_user: with no context, count(*) on clients is 0; with branch A context only branch A rows appear; inserting a row for branch B fails; and an e2e test that deliberately bypasses the Prisma filter still cannot read branch B.
6) Security pass: dependency audit, secret scanning in CI, check no route lacks @RequirePermission, @Roles or @Public, check no raw string SQL exists, check CORS and CSRF, check no sensitive data in logs.
7) Rate-limit and performance checks: e2e tests for the login lockout, OTP limits, global token bucket and Retry-After; a k6 or autocannon load test of the key endpoints (client list, daily schedule, dashboard) that reports p95 latency and Prisma query counts; fix any endpoint whose query count grows with row count.
Done when: RLS blocks cross-branch access in the tests above, all security checks pass and the load test results are recorded in the README.
