Implement schedules (recurrence rule, start time, duration) and appointments. Creating a schedule generates appointments through a BullMQ job for a rolling window (for example 8 weeks) and a nightly job extends it. Conflict detection for therapist and client returns clear 409 errors (the DB exclusion constraint is the last line of defence). Endpoints: weekly calendar GET /appointments?from&to&therapistId&departmentId&status (date range limited to 31 days, selects only client name, department, therapist first name, status, times and cancel reason; cancelled appointments stay in the result), reschedule, cancel (reason required, notifies the parent through the communication queue), mark attended / no-show. Session history per client uses cursor pagination. Leave and holidays flag affected appointments. A therapist sees only their own appointments; a parent gets a read-only schedule for their children.

DAILY SCHEDULE CACHE: add GET /appointments/daily?date&branchId. Cache the branch-day schedule in Redis under schedule:{branchId}:{yyyy-mm-dd} (non-sensitive display fields only: appointment id, client display name, department, therapist first name, start/end, status). Build it with one query using select. TTL: 5 minutes for today, 1 hour for other dates, and explicit invalidation of that key on every create, reschedule, cancel, attendance mark, schedule change and approved leave. A nightly job warms tomorrow's key for every branch. AFTER reading from the cache, apply the caller's scope in the service (therapist: own only; parent: own children only; manager and director: branch rows) so a shared key never leaks rows. If Redis is down, fall back to the database. Send Cache-Control: no-store on the HTTP response.
