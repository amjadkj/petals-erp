Implement the access module, RolesGuard and PermissionGuard.
1) Seed the four roles (with keys) and default module toggles and action permissions. Defaults: Director all on; Manager: dashboard, appointments, clients (administrative data only), communication, financial (payment due and monthly tracking, no P&L), HRMS, employees (no salary), leads, reports; Therapist: dashboard, own appointments, assigned clients, own leave/attendance, own reports; Parent: own child only, view-only, dashboard, schedule, overview, payment plan (status only), assessment and reports only when shared.
2) @Roles(...) and RolesGuard for fixed Director-only routes. @RequirePermission(module, action) and PermissionGuard check, in order: module enabled for the role, user override, role action, then attach a scope (OWN / ASSIGNED / ALL) to the request context for the service. VIEW without VIEW_ALL = scoped; Create/Update/Delete require VIEW. Register guards globally in the order Auth, Roles, Permission. The Director is always allowed.
3) Director endpoints: list/update role modules and permissions, list/update user overrides, GET /me/permissions (full map for the UI). Cache resolved permissions in Redis per user and role; invalidate immediately on any change to a role, override, user role or branch assignment.
4) Every permission change writes an audit entry (use a temporary interface until Phase 6).
Done when: e2e tests prove: a disabled module returns 403; a therapist cannot read another therapist's client; a manager cannot read assessments; an override beats the role; the Director cannot be locked out; permission changes apply on the very next request; a test fails when any route lacks @RequirePermission, @Roles or @Public.
